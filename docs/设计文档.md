## 1. 设计目标与范围

### 1.1 目标

系统对不同文档类型采用**最适配的解析、检索与生成策略**，实现统一、准确、可溯源、多模态的 PDF 智能问答。

- **精确**：手册类回答有结构化引用（`page_no + bbox + chunk_id`），可前端高亮定位。
- **多模态**：宣传册回答可附带图片证据（`imageRefs`）。
- **可插拔**：解析器、检索器、向量库、LLM 全部走接口抽象，换厂商只改实现/配置。
- **可演进**：版本管理、多语言、多轮、反馈闭环、模型版本记录均已预留。

### 1.2 范围（当前骨架已覆盖）

| 能力 | 覆盖情况 |
| --- | --- |
| 文档接入（双链路路由） | ✅ 已实现（骨架级） |
| 分类路由（查询端） | ⚠️ 仅支持人工声明，自动识别为待办 |
| 文档类型自动判定 | ❌ 骨架已移除，改为「管理员声明优先」（见 §6.1） |
| 手册混合检索（BM25 + 向量 + RRF） | ✅ 已实现（BM25 内存精排 + SQL 向量余弦） |
| 宣传册多模态检索 | ⚠️ 骨架：先复用关键词检索，视觉检索待办 |
| 重排序（Rerank） | ❌ 待接入（需求 FR4） |
| 问答 + 引用溯源 | ✅ 已实现（模型标注 `[n]` 序号解析） |
| 多轮对话 | ⚠️ 契约已定义，`history` 尚未注入（上层未接会话存储） |
| 反馈闭环 | ✅ 已实现（点赞/点踩/人工修正） |
| 向量库 / embedding | ✅ SQL Server 2025 原生 `VECTOR` + `/embeddings` |
| 模型版本记录/重建机制 | ✅ `embedding_model`/`dimension` 落库 + 启动维度校验 |

### 1.3 术语对照

沿用《需求分析》附录术语表；本设计新增一处口径：

- **文本链路 / 视觉链路**：分别指「宣传册解析时的 PdfPig 文本抽取」与「页面渲染 + 视觉模型识别」两条**入库解析路径**。

## 2. 总体架构

### 2.1 分层与依赖方向

严格单向依赖（依赖倒置）：**外围依赖内围，内围不依赖外围**。

```
┌─────────────────────────────────────────────────────────────┐
│  Api（表现层）                                              │
│  Controllers · Program.cs · appsettings.json                │
├─────────────────────────────────────────────────────────────┤
│  Application（应用层）· 用例编排                             │
│  DocumentIngestionService · QuestionService · FeedbackService│
│  IDocumentRouter · IRagOrchestr · DTOs                      │
├─────────────────────────────────────────────────────────────┤
│  Domain（领域层）· 实体 + 端口（零依赖）                     │
│  Entities · Enums · ValueObjects · Abstractions(I*端口)      │
├─────────────────────────────────────────────────────────────┤
│  Infrastructure（基础设施层）· 实现                          │
│  Pdf · Vision · Embedding · LLM · Retrieval · Data · 路由编排 │
└─────────────────────────────────────────────────────────────┘
```

依赖方向：`Api → Infrastructure → Application → Domain`。
关键约束：**Domain 不认识 Application/Infrastructure；Application 只依赖 Domain 的接口，不依赖任何实现类**。具体实现一律由 Infrastructure 在启动时经 DI 注册（见 `DependencyInjection.AddRagInfrastructure`）。

## 3. 核心流程

### 3.1 文档接入（入库管线）

入口：`POST /api/documents/import`

```
ImportDocumentRequest(filePath, version, documentType?, language?)
        │
        ▼
[1] 确定类型：declared = request.DocumentType ?? Manual
        │
        ├── Manual ──► [2a] PdfPigTextExtractor.ExtractAsync  ──► 按页产出 Text/Word/尺寸
        └── Brochure ─► [2b] 逐页 RenderAsync(PNG) ─► VisionExtractor.RecognizeAsync
                            ──► 每页一个内容块（视觉转录 + 版面描述）
        │
        ▼
[3] WriteChunksAsync：为每条块生成 embedding（批量），写 SqlServerChunkStore（MERGE）
        │
        ▼
[4] repository.UpsertAsync(document)：登记元数据（MERGE + 维护 is_latest）
        │
        ▼
返回 ImportDocumentResult(documentId, version, chunkCount, type, typeSource, notes, warnings)
```

**关键设计——输入类型由声明决定，不做自动判定**：骨架刻意移除自动分类器。原因：自动判定的三信号（可读占比/文本密度/图片密度）在真实数据上置信度不足，与其用弱判定引入误路由，不如由**管理员声明**＋保留告警。宣传册未声明时按 Manual 走文本链路，若抽到空文本会给出「可能需改为视觉链路」的告警（见 `ParseManualAsync` 的空文本告警）。

**宣传册为何走视觉链路而非文本抽取**：工业 PDF 常使用内嵌 CID 子集/预定义 CMap 字体，PdfPig 纯文本抽取会产出乱码；且宣传册信息以版面视觉为主。视觉模型读像素，绕开文字层编码问题，且能保留版面语义（配图、卖点排布、型号矩阵）。

**一致性问题处理**：三条 AI 能力（生成/视觉/向量）为独立端点，各自可未配置。上传链路对生成能力不依赖；对视觉未配置返回 `Succeeded=false` 并作告警；对 embedding 未配置抛异常被捕获转为告警——**任何能力缺失都不阻塞文档落库**，但会如实告知。

### 3.2 问答（在线管线）

入口：`POST /api/questions`

```
QuestionRequest(question, conversationId?, documentType?, version?, language?, documentId?)
        │
        ▼
[1] router.RouteAsync：type = request.DocumentType ?? Manual   （自动识别为待办）
        │
        ▼
[2] 按类型选择检索器
        ├── Manual ──► IHybridRetriever.RetrieveAsync
        │             ├─ 关键词路：SqlServerChunkStore.KeywordSearch（中文 bigram → LIKE 粗筛 → BM25 精排）
        │             ├─ 向量路：Embedding(question) → SqlServerChunkStore.VectorSearch（VECTOR_DISTANCE 余弦）
        │             └─ RRF 融合（multiplicative），向量路失败自动单路降级
        └── Brochure ─► IMultimodalRetriever.RetrieveAsync（骨架：复用关键词检索）
        │
        ▼
[3] orchestrator.AnswerAsync(context, history=null, ct)
        │
        ▼
[4] ILlmClient.CompleteAsync：上下文编号注入 → system 强制用 [n] 标注依据 → 解析 UsedContextIndexes
        │
        ▼
[5] CitationBuilder：仅取「模型真正标注引用」的 chunk → page_no+bbox+chunk_id
[6] 置信度 = 引用条数 / 上下文条数（覆盖率，可解释而非校准概率）
        │
        ▼
返回 QuestionResponse(answer, citations, imageRefs, confidence, documentType, version)
```

检索预览（`POST /api/questions/retrieve`）：只跑检索不调生成，用于在无模型时观察召回是否正确。

### 3.3 反馈

入口：`POST /api/feedback`。`FeedbackService` 将请求原样映射为 `QaFeedback` 落库（`qa_feedback` 表）。支持点赞/点踩/修正答案（`corrected_answer` 回写为黄金标注，FR9）。

## 5. 基础设施实现（Infrastructure）

### 5.1 PDF 文本抽取 —— `PdfPigTextExtractor`

- 基于 **UglyToad.PdfPig**，逐页取整页文本、词项坐标与页尺寸。
- 兜底：`page.Text` 归一化后为空时退化为「按词项重组」（`ExtractPageWords` 包 try/catch，单页词项失败不影响整份文档）。
- 产物供手册链路切片、混合检索、bbox 溯源使用。

### 5.2 页面栅格化 —— `PdfiumPageRenderer`

- 基于 **PDFtoImage（PDFium）+ SkiaSharp**，`RenderAsync` 为 `IAsyncEnumerable<PdfPageImage>`，逐页渲染即编码 PNG（质量 100），位图用完即释放——**内存占用与页数无关**，适合大文档。
- 默认 `RenderDpi=120`（实测单页约 992×1403，400~600KB，文字与参数可辨识）。
- 注意：PDFium 仅支持桌面/服务端平台（已用 `[SupportedOSPlatform]` 声明）。

### 5.3 视觉识别 —— `OpenAiCompatibleVisionExtractor`

- 调 OpenAI 兼容 `/chat/completions`，`messages` 含 `image_url`（`data:image/png;base64,...`）。
- 强制两个行为（镜头内不推断）：**逐字转录保留型号/参数/编号/单位**、**表格用 Markdown 还原**；**看不清写「无法辨认」不猜测**。
- 降级策略：未配置 → 返回 `Succeeded=false` + 原因；失败 → 同前返回错误，入库流程继续并把原因作为告警返回（不抛 500）。

### 5.4 Embedding —— `OpenAiCompatibleEmbeddingProvider`

- 调 `/embeddings`，支持批量（`EmbeddingBatchSize` 默认 10，服务端有批次上限），返回数与请求数不匹配立即失败。
- 未配置抛 `InvalidOperationException`，由接入方捕获转为告警（与视觉一致）。
- `EmbedImageAsync` 当前抛 `NotSupportedException`——多模态向量需 CLIP 类模型且百炼不支持 OpenAI 兼容接口，**宣传册图文向量对齐是已知未实现项（FR5/多模态对齐）**。

### 5.5 文本生成 —— `OpenAiCompatibleChatClient`

关键设计：**把上下文片段编号注入 user prompt，强制模型在答案中用 `[序号]` 标注依据**，再用正则 `\[(\d+)\]` 解析出 `UsedContextIndexes`。这让引用「可信」——用户能分辨哪条真正支撑了答案，而不至于把全部召回当引用。

- `temperature=0`（确定性优先）。
- 上下文超 `MaxContextChars=20000` 截断。
- 未配置/调用失败**不抛异常**，返回带 `【生成模型未配置】`/`【生成模型调用失败】` 前缀的降级答案——把「模型不可用」如实告诉用户而非伪装成功或返回 500。
- 系列 prompt 要求不编造；检索为空直接答「资料中未找到相关内容」。

### 5.6 混合检索 —— `RrfHybridRetriever`

- 两路并行：关键词路（`SQL LIKE` 粗筛 + 内存 BM25 精排）+ 向量路（余弦距离），`Task.WhenAll` 并行发起。
- 用 **RRF（Reciprocal Rank Fusion）** 融合两路排序，`TopK * 3` 每路候选，给融合留挑选空间。
- 设计取舍：关键词擅长**精确串**（型号/故障码/参数），向量擅长**语义改写**（"怎么接线"召回"配线步骤"）；缺一路会在对应场景失准。
- **向量路尽力而为**：向量化失败（未配置/超时/服务不可用）自动退化为单路关键词，不全链路失败。

### 5.7 多模态检索 —— `InMemoryMultimodalRetriever`

骨架实现：目前 `RetrieveAsync` 直接复用关键词检索（`store.KeywordSearchAsync`）。`image-ref` 参与检索、图文 embedding、视觉检索均标注为**待视觉索引就绪后实现**。

### 5.8 RAG 编排 —— `RagOrchestr` / `CitationBuilder`

- 编排：调 LLM → `CitationBuilder.BuildCitations` → 组装 `QuestionResponse`。
- 引用只含「模型标注引用」的 chunk（`usedIndexes` 空则返回空引用，杜绝「引用全部上下文」）。
- 置信度 = `引用条数 / 上下文条数`（覆盖率）。文档注释明确：这是可解释的覆盖率，**不是校准概率**；待评估集建立后替换为 RAGAS 的 faithfulness/relevancy。
- `ImageRefs` 从上下文收集含 `ImageRef` 的块——宣传册答案可附带图片证据。

### 5.9 数据层 —— `SqlServerDocumentRepository / SqlServerChunkStore / SqlServerFeedbackRepository`

- 全部 Dapper，异步 + `CancellationToken` + 事务。
- **`is_latest` 语义**：由 `DocumentRepository.UpsertAsync` 统一维护（先清掉该文档其他版本标记，再把本次版本标为最新）——**「最新 = 最近一次导入的版本」**。修复前曾在首次导入才置位，导致新版本导入后旧版仍被当成最新，检索默认命中最新版时返回旧内容。
- **`SqlServerChunkStore`（关键字 BM25）**：
  1. 中文标题/文本 bigram 分词；
  2. 语料统计（chunk 总数、平均长度、每词文档频率，一次 SQL 条件聚合 + `CONCAT` 拼 DF 列表）；
  3. 粗筛 `LIKE`（转义 `%`/`_`/`[`），候选上限 2000；
  4. 内存 BM25 精排取 topK。
- **向量检索**：SQL Server 2025 原生 `VECTOR(n)` + `VECTOR_DISTANCE('cosine', ...)`，未建向量索引时暴力扫描排序（对万级足够）。向量以字面量 `[0.1,0.2,...]` 传入。**维度不匹配静默失效 → 启动校验直接报错**（见 §5.10）。
- `Columns()` 显式列清单而非 `SELECT *`（避免 VECTOR 列映射异常），并用 `LEFT JOIN document` 一次带出 `title`（引用展示需它）；过滤默认 `d.is_latest=1`（未指定版本时）。

### 5.10 数据库初始化 —— `DatabaseInitializer`

- 启动时：建库（连 `master`）→ 分批执行 `schema.sql`（按 `GO` 拆批）→ **校验 `chunk.embedding` 列维度与配置一致**。
- 维度校验：读 `sys.columns.max_length`，`VECTOR(n)` 存储长度 = `n×4+8`（实测 VECTOR(3)=20 / VECTOR(1024)=4104），据此反推列维度；不一致抛明确异常（FR10「换 embedding 模型必须重建索引」的落地机制）。

## 6. 关键技术决策与理由

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 入库类型**由管理员声明驱动**，不做自动判定 | 自动分类信号置信度不足，弱判定误路由比「声明 + 告警」危害更大；为标注集铺路仍记录源 |
| D2 | 宣传册走**渲染→视觉识别**，不走纯文本 | 绕开 CID 字体乱码；版面语义/卖点排布/型号矩阵只有视觉可还原 |
| D3 | 引用只暴露「模型标注」片段 | 避免把全部召回当引用，否则置信度恒为 1 且掩盖「答案无依据」的真相 |
| D4 | LLM/视觉**不配置或失败不抛错**，返回带标记的降级结果 | 问答接口应如实告知「模型不可用」，而非 500 或伪装成功 |
| D5 | 向量路失败**自动降级单路关键词** | 关键词路独立可用，没理由被向量路拖垮 |
| D6 | 向量存 SQL Server 2025 原生 `VECTOR` | 省去 Milvus/Qdrant，工业内网离线部署更简单 |
| D7 | `is_latest` 统一由仓储维护 | 保证「最新=最近导入」，规避首页检索返回旧内容 |
| D8 | DPI/批量/超时等全进 `appsettings`（`Ai` 节） | 三项 AI 能力独立配置，便于跨厂商替换 |
| D9 | 全异步 + `CancellationToken`（含 Dapper `CommandDefinition`） | 高并发 I/O 不占线；取消可贯穿到数据库 |

## 8. API 设计

### 8.1 端点一览

| 方法 | 路径 | 作用 | 入参 | 出参 |
| --- | --- | --- | --- | --- |
| POST | `/api/documents/import` | 文档接入 | `ImportDocumentRequest` | `ImportDocumentResult` |
| POST | `/api/questions` | 统一问答 | `QuestionRequest` | `QuestionResponse` |
| POST | `/api/questions/retrieve` | 检索预览（不调生成） | `RetrievalPreviewRequest` | `RetrievalPreviewResponse` |
| POST | `/api/feedback` | 反馈闭环 | `FeedbackRequest` | 200 |

> 端点均无鉴权/限流（骨架阶段），生产需按需求 NFR 补 RBAC、审计、限流。

### 8.2 文档接入

请求 `ImportDocumentRequest`：`filePath`(必)、`version`、`documentType?`、`language?`。
响应 `ImportDocumentResult`：`documentId`、`version`、`chunkCount`、`documentType`、`typeSource`、`parseNotes[]`、`warnings[]`。

### 8.3 问答

请求 `QuestionRequest`：`question`(必)、`conversationId?`、`documentType?`、`version?`、`language?`、`documentId?`。
响应 `QuestionResponse`：
```
{
  conversationId, answer,
  citations: [{ documentId, documentTitle, version, chunkId, pageNo, section, bbox:{x,y,width,height}|null }],
  imageRefs: [string],        // 宣传册图片证据
  confidence, documentType, version
}
```

检索预览 `RetrievalPreviewRequest`：`query`、`documentId?`、`version?`、`language?`、`topK`(默认10)。
响应 `RetrievalPreviewResponse`：`query`、`count`、`chunks:[{chunkId, documentId, documentTitle, version, pageNo, section, textPreview}]`（`textPreview` 截断防响应过大）。

### 8.4 反馈

`FeedbackRequest`：`conversationId`、`question`、`answer`、`isUpvote`、`rejectionReason?`、`correctedAnswer?`。

### 8.5 示例（问答响应）

```json
{
  "conversationId": "a1b2...",
  "answer": "按 E-203 故障码，应断电后检查进线端子是否松动[0]、查看主控板指示灯状态[3]。",
  "citations": [
    { "documentId": "pm-k45", "documentTitle": "PM 系列使用手册", "version": "2.0",
      "chunkId": "pm-k45:2.0:p12", "pageNo": 12, "section": "故障处理",
      "bbox": { "x": 42, "y": 210, "width": 480, "height": 36 } }
  ],
  "imageRefs": [],
  "confidence": 0.5,
  "documentType": "Manual",
  "version": "2.0"
}
```

## 9. 配置（appsettings.json 的 `Ai` 节）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `Ai:Chat:{BaseUrl,ApiKey,Model}` | 达模型兼容地址 | 文本生成（DeepSeek 等 OpenAI 兼容） |
| `Ai:Vision:{BaseUrl,ApiKey,Model}` | 同上 | 宣传册视觉识别 |
| `Ai:Embedding:{BaseUrl,ApiKey,Model}` | — | 向量化（DeepSeek 官方无 embeddings，需另配百炼/硅基流动等） |
| `Ai:EmbeddingDimensions` | 1024 | 必须与 `chunk.embedding` 维度一致，启动校验 |
| `Ai:EmbeddingBatchSize` | 10 | 每次向量化最多条数 |
| `Ai:RenderDpi` | 120 | 页面渲染清晰度 |
| `Ai:VisionTimeoutSeconds` | 180 | 视觉超时 |
| `Ai:EmbeddingTimeoutSeconds` | 120 | 向量化超时 |

> `ApiKey` 不得写入纳入版本控制的 `appsettings.json`，应放 `appsettings.Development.json` 或环境变量。`AiEndpointOptions.IsConfigured` 三项齐全才算配置完成。

## 11. 可演进性与约束

- **可插拔**：换 PdfPig→其他、换存储→Milvus/Qdrant、换 LLM/上重排，只动 Infrastructure 实现，上层契约不变。
- **离线部署**：视觉/生成/向量均可内网私有化即可，无需云厂商绑定（只要 OpenAI 兼容协议）。
- **向量维度变更成本**：换 embedding 模型维度变化需 `ALTER TABLE` 重建 `embedding` 列并全量重导（已内置校验保障不致静默失效）。
- **并发/性能**：全异步 + 检索与视觉调用可并行；上传大文档的渲染为流式逐页释放内存。
